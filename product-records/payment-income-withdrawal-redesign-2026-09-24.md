## 1. 目标与决定边界

目标：需求方微信付全款，个人服务方完成服务并通过验收，平台按订单取得20%，服务方取得80%的税前应结收入；服务方能够明确查看收入来源、可提现金额和真实到账结果。

本次借鉴爱发电的“支付—收入核算—达到结算条件—余额可提现—申请提现”体验。爱发电官方指南公布6%费用、94%创作者收入及次月1日入账；其底层收单、资金归属及代付接口并未完整公开。本方案不是复制爱发电未经证实的内部实现，也不采用其月结日或6%比例。

| 已确定 | 本方案建议，尚未变为已执行规则 | 必须依渠道或经营决策确定 |
| --- | --- | --- |
| 微信收款、合作确认后全额预付、验收后结算、平台20%、服务方80%、个人供给 | 验收及渠道结算完成后可申请提现；首版一个有效本人收款账户；支付及提现通道费用从平台20%承担；不额外收用户提现费 | 获批交易角色/渠道、支持的收款账户、到账时效及限额、税务扣缴/开票安排、已结算退款资金来源、未成年人交易资格 |

## 3. 支付与资金流程

### 3.1 渠道前提

优先核验可接受本业务的支付机构平台交易结算产品，继续以通联云商通为候选。除微信收款、个人收款、80/20、验收结算之外，必须确认“可由用户主动申请出款”能力及最长持有期限。若产品只支持自动结算到银行卡，就不能再制造一个可以重复提款的本地余额；应改为自动到账记录，并在实施前说明与本方案的差别。

理想资金结构：资金由获准机构按订单及真实交易角色管理；万匠屋记录业务和资金指令，不自行建设可充值、转赠或消费的储值钱包。平台账本是业务核算记录，不是独立支付账户。机构托管、担保、簿记账户等术语须按批准合同使用，不笼统宣传银行托管。

### 3.2 买家付款

1. 服务方提交收款资料并经渠道核验；不具备收款条件时，可以浏览/沟通，但不能让买家支付该服务方订单。
2. 双方确认服务、金额、时间及协议；服务端生成订单与计费快照。前端只传订单标识和操作凭证，不传可信费率、收款方或付款结果。
3. 点击“微信支付”，服务端核对订单版本、付款身份、服务方资格、可支付时段和渠道最长履约期限，创建支付单并调起微信。
4. 微信客户端返回后，页面查询服务端状态；以验签通知或可信查单为付款事实。取消/断网不能直接判为未支付并重新收款。
5. 支付确认后订单进入履约，服务方资金页增加80%预计收入至“待结算”；此时不产生可提现金额。
6. 关单与晚到支付竞争时，查询核实原交易；异常实付进入待核对及退款处置，不静默丢弃、不生成第二笔履约收入。

### 3.3 验收与结算

1. 需求方在原交付页确认验收；保留现有验收条件，不能为了资金到期自动确认服务完成。
2. 订单完成与结算意图持久化；已有 settlementIntent/结算任务承担此衔接，提交丢失可恢复。
3. 结算任务核对已付款、无退款/争议冻结、资料有效、计费快照和渠道条件；按原任务编号提交并查询。
4. 渠道确认双方分配结果后分别记账。平台佣金成功不能代表服务方资金已可支取；只有服务方份额实际达到渠道可支取状态，才从“待结算”转入“可提现”。
5. 结算失败继续待结算，显示具体可处理原因；通知管理员，不要求需求方重复付款或重复验收。
6. 长履约订单在付款前校验时长。临近渠道资金释放上限时告警并处置延期/退款；不得依赖无限冻结。

### 3.4 金额口径

金额全部按人民币整数分保存；沿用 `fee-policy.js` 的20%取整规则：平台份额为 `(金额分 + 2) / 5` 的整数商，服务方份额为总额减平台份额。规则版本逐付款快照，历史单不随新规则重算。

例如100元有效服务金额，平台20元、服务方80元税前。通道成本单独列为平台费用，不能从双方名义份额中重复扣。税额仅按已确认的扣缴责任、计算结果及凭证入账，不自行编税率。

退款以累计有效金额重新计算应保留份额，差额作冲正，避免多次按每笔退款独立取整造成累计误差。例：100元退30元，剩余70元的平台份额14元、服务方56元；相对原单分别冲正6元、24元。历史计费快照不被覆盖。

## 5. 提现全过程与异常

正常流程：我的收益 → 提现 → 输入金额/全部提现 → 核对本人账户、费用和预计实到 → 完成需要的验证 → 提交 → 处理中 → 渠道确认到账 → 已到账。

首版建议随用户申请提交，而非照搬爱发电按月结算；到账速度以批准渠道为准。最低金额、单笔/日限额、节假日时效全部来自生效渠道规则，不写死10元或T+1。最终规则未装配时提现保持不可提交，并显示业务原因。

| 内部状态 | 用户看到的状态 | 余额处理及下一步 |
| --- | --- | --- |
| RESERVED | 已提交 | 数据库事务锁定可用额，将其转入提现占用；同一操作重复提交返回原单 |
| REVIEW_REQUIRED（仅必要时） | 待审核 | 保持占用；管理员核验证据，不人工改余额 |
| PROCESSING / UNKNOWN | 银行处理中/结果确认中 | 保持占用；网络超时查原提现编号，不能释放后重付 |
| SUCCEEDED | 已到账 | 依据渠道最终成功含义及流水确认出款，扣减占用；若成功仅表示已发送银行，则继续处理中 |
| FAILED_FINAL | 提现未成功 | 确认未出款且无后续在途资金后解除占用；存在退款/争议时转冻结或退款占用，不盲目恢复可提现 |
| CANCELLED | 已取消 | 仅未发送渠道且可安全取消时；与任务领取互斥后解除占用 |
| RETURNED | 款项已退回 | 已出款后银行退票作为新事实入账，收到渠道资金退回证据后恢复对应金额；不能删除原成功流水 |

余额不足、低于限额、资料过期、渠道暂停在提交前明确提示。处理中的请求不能因页面返回/退出登录取消。失败重试先确认原单最终未出款，再以新的用户申请关联原失败单；底层请求不因超时更换编号。

一笔提现可以覆盖多笔已结算订单，需要逐订单分配占用金额，以支持后续退款与对账。首版按可提现时间从早到晚分配，不让用户手动选订单。多设备同时提取通过同一资金账户锁和数据库唯一键防止超提。

| fund_journals + fund_postings | 新增不可覆写账本 | journal含事件类型、业务ID、唯一事件键、规则版本、时间、冲正原记录；posting含资金科目/所有者、订单、币种、借贷方向、整数分；每笔记账借贷平衡，纠错新增冲正 |
| fund_balances | 新增交易用余额快照 | provider、currency、pending/available/held/withdrawing分桶、version；唯一账户，事务内与账本同时更新，禁止负可用额；可从账本重建 |
| withdrawals | 新增提现单 | provider、申请幂等键、账户版本快照、扣账总额、费用、税额、预计实到、规则快照、渠道单号、状态、查询/重试时间、租约；provider+幂等键唯一 |
| withdrawal_allocations | 新增提现来源 | withdrawal_id、原结算/订单、分配金额；锁定来源剩余额度，金额合计与提现占用一致；支持合并提现及部分退款追溯 |
| payment_channel_events | 新增渠道事件收件记录 | channel、事件唯一标识、业务单号、验签结果、载荷摘要、处理状态/次数；与业务状态及记账幂等；敏感回执另限权加密存放 |
| payment_reconciliation_items | 新增对账批次/差异记录 | 账单日期/渠道/批次、文件hash、业务单号、差异种类/金额、证据、处理人/复核人、关闭状态；同账单重复导入不重复差异 |
| order_funds_interlocks / payment_mutation_receipts | 复用并按需要扩展 | 退款争议与资金动作互斥；请求防重不替代账本业务事件唯一约束 |

这些为支付业务子账，不取代公司法定会计账簿。科目至少区分渠道资金、待结算服务款、服务方可用/冻结/提现占用、平台服务费、退款、通道成本及适用税款，不只用一个可编辑balance字段。

关键一致性规则：

1. 正常100元订单记录总交易事实100、平台20、服务方80；可提现必须有机构支持的可支取资金对应，不能仅凭本地分账运算生成。
2. pending/available/held/withdrawing为互斥当前分桶；已到账是历史流量，不加入当前余额合计。税在结算时已扣则提现不能再扣。
3. 提现总扣账额 = 实际出款净额 + 本次适用手续费 + 本次适用税额；平台承担的费用走平台费用账，不从服务方扣账。显示“到账预计”与最终值的差异须有依据，不能事后任意增扣。
4. 提现申请在同一数据库事务内完成余额校验、占用、来源分配、提现单和账本写入。渠道网络调用在事务外进行；持久化任务恢复既有租约模式，不长时间占数据库锁。
5. 回调事件防重、状态更新、账本过账同事务；乱序回调不把成功降级。矛盾终态进入人工核对，不能自动再付。
6. 退款和提现同时锁涉及资金账户及来源订单，统一锁顺序；若提现已发送不能抢占同一在途款退款，转入售后资金待处理。
7. 时间存统一时间戳，界面及账单业务日使用Asia/Shanghai；渠道账单日期与时区单列，跨日不以设备日期判断。
8. 金额使用安全整数边界；MySQL BIGINT返回如可能超过JS安全范围则字符串/BigInt计算，不经浮点元运算。

## 7. 接口与执行责任

复用可信微信身份入口及现有payment-api/order-api；资金动作仍由服务端执行。客户端不能提交任意provider_id替他人提现，也不能提交“已支付/已到账”作为事实。

| 能力 | 输入重点 | 输出/责任 |
| --- | --- | --- |
| getIncomeSummary / listIncomeEntries | 当前身份、合法筛选、游标 | 互斥余额、统计口径、脱敏流水及更新时间 |
| startPayoutOnboarding / getPayoutProfile | 当前身份、渠道所需授权 | 机构采集会话与核验状态；返回小程序后由服务端确认 |
| quoteWithdrawal | 金额、当前账户版本 | 可用额、规则、费用/税额、净额、失效时间及quote_id |
| createWithdrawal | quote_id、幂等键、必要验证凭证 | 重新核对账户及余额；变化则重新确认，不能静默换收款卡；返回唯一提现单 |
| getWithdrawal / listWithdrawals | 本人提现编号/游标 | 查本地可信进度，必要时服务端受控查渠道，不在页面高频轮询 |
| refund申请/审核/查询 | 原付款单、原因、范围、幂等键 | 买家提申请，后台决策；退款受理与成功分别保存 |
| settlement/payout worker | 持久化待处理任务 | 原编号提交/查单、结果回写、退避重试、异常告警 |
| 渠道回调/对账导入 | 验签通知/授权账单 | 防重、处理、对账；拒绝客户端伪造 |

报价只为明确本次扣款，不保障余额直到提交都不变化。未通过机构验证的收款账户不能创建提现。渠道凭据存受控配置，业务账号最小权限；前端永远拿不到支付私钥或未脱敏金融资料。

## 8. 退款、争议与冻结

| 时点 | 处理原则 |
| --- | --- |
| 未结算 | 先冻结对应待结算款，按审核结果原路退款；成功后冲正服务方与平台应计份额，失败保持可追踪状态 |
| 已可提现、未申请 | 冻结对应订单尚未出款金额；不得冻结无关订单全部收入；有合法约定的跨订单追偿须另有依据 |
| 提现处理中 | 先查在途提现是否可取消；不可取消/结果未知时不释放占用，售后继续处理但明确退款资金来源 |
| 已到账 | 无自动追回假设；按已签约渠道回退、服务方退回或获批平台垫付处理，不能通过改负余额假装已退款 |

平台垫付额度和售后责任需定案；首版未获授权不自动垫付。若因此存在无法完成正常售后的情形，应视为上线阻塞，而不是把责任推给用户等待。冻结必须有对象、金额、原因、案件号和解除条件；客服可看原因，只有资金权限人员能执行获准动作。

## 9. 支付数据维护与管理端

不直接用SQL改支付状态或余额。管理能力可接现有管理入口；若当前没有安全管理端，首期建设最小内部受控页面，不额外重建全业务后台。

| 工作台 | 必要能力 |
| --- | --- |
| 资金总览 | 交易总额、退款、平台服务费、渠道成本、服务方应付/已付、提现在途、异常差异；每个指标有时间及口径 |
| 交易检索 | 通过内部UID/订单/付款/渠道单号查整条链，查看脱敏资料及事件时间线 |
| 收款资料 | 审核状态同步、缺项、过期、暂停原因；平台手工审核不能覆盖机构拒绝 |
| 提现维护 | 待审/在途/超时/失败/退票列表；查原单、处理补充资料、受控重试，不提供任意改收款人或强制成功按钮 |
| 退款争议 | 证据、审批、冻结/解除、退款来源、执行结果；高风险资金动作双人复核 |
| 日对账 | 自动导入机构支付/退款/分配/出款/费用账单，与本地业务单及账本比对；漏单/重复/金额/状态差异逐项处置 |
| 规则与审计 | 有生效时间的费率和渠道限制、操作人/复核人、原因、前后值及关联单据；规则变更不重写历史单 |

实时处理回调，定时查未决任务；每日按渠道账单可用时间完成对账，次日处理差异。建议上线目标：未决超渠道承诺时效自动告警；金额不一致或疑似重复出款立即暂停相关资金动作，保留查单与退款必要能力。值守人、通知渠道及响应时限必须上线前落实，不默认全天人工审核正常提现。

备份包含业务单、账本、事件和审计，恢复后先与机构核对再恢复出款，防止备份回滚重复打款。敏感信息加密、访问留痕、导出脱敏和限权；保留期限按实际产品合同及适用义务确定，不能让普通账号注销或媒体清理删除应保留的交易证据。

## 10. 用户提现指南初稿

以下是待渠道参数确定后可发布的帮助内容；没有确定的时效和限额不以占位数字发布。

**怎样开通收款？** 切换到服务方，在“我的收益—收款设置”完成实名认证、本人收款账户验证及相关协议。审核结果会在页面显示，需要补充资料时按提示完成。

**买家付款后为什么暂时不能提现？** 这笔收入会先显示在“待结算”。服务验收完成，且支付机构确认达到结算条件后，会转入“可提现”。有退款或争议的款项会单独显示处理状态。

**怎样提现？** 打开“我的收益”，点击“提现”，输入金额或选择全部提现，核对收款账户、费用及预计实到金额，确认后提交。进度可在“提现记录”查看。

**多久能到账？** 申请页显示当前收款方式的预计到账时间。银行处理、节假日或资料核验可能影响进度；超过显示的预计时间，可从提现详情联系客服。

**提交后金额为什么减少？** 申请金额已转入“提现中”，不会再重复显示为可提现；到账后可查看成功记录。未成功且确认资金已释放时，金额会按实际情况退回可提现或转入相关售后处理。

**能否提到他人账户？** 不可以，请使用本人通过验证的收款账户。更换账户需重新验证；已提交提现仍使用提交时确认的账户。

**为什么显示结果确认中？** 系统正在核对支付机构的最终结果，同一笔申请不需要重复提交。

**平台收多少费用？** 每笔有效服务金额按20%计平台服务费，80%计服务方税前应结收入。提现页会列出本次实际适用的费用、税款及预计实到；最终费用承担规则将在开通协议中明确，避免重复扣费。

## 11. 实施顺序与验收

| 阶段 | 交付 | 通过标准 |
| --- | --- | --- |
| A 规则及渠道落定 | 个人身份/行业准入、80/20、主动提现、期限、手续费与税务、退款资金方案 | 书面产品/合同依据，能对应真实订单，不用接口支持代替业务获批 |
| B 产品及数据契约 | 本文定案、完整页状态稿、接口字段/资金状态图、最小增量迁移 | 供需页面金额同义，字段采集必要，提现来源可追溯；规则待定项有明确结论 |
| C 本地实现 | 复用现有支付及验收，新增收款档案/账本/提现/维护能力 | 真实MySQL并发及幂等测试，模拟渠道只证明程序逻辑 |
| D 渠道联调 | 签名回调、付款、退款、结算、绑卡及提现查询、账单 | 官方联调环境闭环、未知状态恢复及真实回执语义核验 |
| E 受控部署 | 备份、增量迁移、最小权限、资金关闭发布、只读回查 | 不删除历史流水；监控/对账/恢复可用；实际部署与本地状态分别记录 |
| F 真实资金与发布 | 经授权的小额买卖双方交易、提现、退款及故障恢复 | 付款与出款银行/机构证据和三方对账一致，真机全部页面通过；再按上线门槛开放 |

必验用例：100元及非整元20/80、分次部分退款舍入、重复支付/验收/提现、20并发提现不超额、回调重复乱序、提交成功但响应丢失、提现在途与退款竞争、换卡与提交竞争、证件过期、账户暂停、税费不重复扣、提现退票、任务重启和备份恢复、对账漏单/重单/金额差异、越权查看/提现、双身份返回与冷启动、跨北京时间零点。

产品验收须查看当前完整页面及真机行为：无普通读取过程句、协议默认未勾选、窄屏金额和长银行名称不破版、无重复授权注册、UID不露出、买家首页仍为信息广场。实施时登记新路由与模块，运行design:check及相关测试；静态检查不替代界面验收。

## 12. 上线前必须关闭的决策项

1. 机构对本行业、个人供给、20/80及主动提现是否批准；本人银行卡/其他账户的准确支持范围。
2. 平台是否承担支付/提现费用；真实报价及最低/最高金额、频率、到账期限。
3. 税务扣缴、开票关系、个人年龄及经营资格规则。
4. 已结算退款、争议保障资金与平台垫付边界；不得带着无法处理正常售后的缺口上线。

本轮不要求用户立即填写这一串信息；方案已给出建议方向，具体参数在渠道及商业规则收口时一次确定。
