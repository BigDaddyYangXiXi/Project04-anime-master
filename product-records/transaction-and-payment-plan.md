# 全额预付交易方案与支付接入准备

日期：2026-09-05。承接 [完整需求对账](release-requirements-audit.md) 的 P01—P04、B06 与 B14。状态：全额预付、验收后结算与逐单分成已确认；资金产品、合同条款与售后参数待收口。本文为开发与验收方案，不代表支付开户、资金托管、合同签章或真实交易已经完成。

## 1. 已确认决定与历史替代

| 事项 | 当前依据 |
| --- | --- |
| 产品入口 | 只做微信小程序，微信和支付宝支付均保留目标；支付宝在微信宿主的路径待证 |
| 运营主体 | 公司；尚无微信支付商户号、支付宝商家账号或支付服务商 |
| 付款方式 | 用户明确选择：合作确认后付全款，验收后向服务方结算 |
| 历史替代 | 替代 [需求发现](../requirements-discovery.md) 5.3／5.4 与 [原 PRD](../prd-v0.2-with-logic-diagrams.md) 流程图中的定金＋尾款倾向；原文作为历史保留，首版不再开发分期付款和尾款催收 |
| 订单归属 | 同一服务方的多个服务项目可合为一单；不同服务方分别下单；项目归组不改变单笔订单的付款、验收和结算 |
| 最终验收 | 双身份独立且可切换，完整交易与售后可用；真实数据、两位真实参与者、真实通道结果与品牌 UI 同时验收 |

确认付款方式不等于已确认资金由公司收取或保管。合同卖方、支付收款方、结算受益方、手续费承担者必须在开户方案中分别写明。

## 2. 拟议交易关系

用户已确认优先沿用“需求方与独立服务方就服务直接缔约，公司运营平台并提供售后协调”的定位，但允许为降低平台风险而调整，最终要求是每笔合作稳定获得分成。具体合同条款、平台责任、税务与开票关系仍需结合实际经营和支付产品确认；如改为公司承接服务再采购，应重新评估订单合同和支付模式，不能仅改页面名称。

资金方案的选择标准：所选支付机构产品须支持本行业与服务方类型，能按订单记录全额付款、验收后的结算、取消退款及已结算售后处理。先取得适用性证据，再定收款账户和具体接口；不将“全额预付”解释为给平台自建余额充值。

**商业规则更新**：按每笔合作收取平台分成已由用户明确，替代历史“尚未确定收费／不向个人交易收费”的不一致口径。比例或金额、分成计算基数、支付手续费承担和退款后分成处理仍待确定，不写入任意默认费率。

### 2.1 以降低平台资金与履约风险为目标的支付选型

优先核验方向：服务方以支付产品认可的商户身份收款，交易资金在支付机构提供的账户体系中按约处理；验收达到结算条件后，支付机构将约定平台服务费分给公司、剩余金额按规则结算给服务方。公司记录订单与资金指令，不自行建立储值资金池。该方向是风险控制建议，能否适用必须取得行业和商户准入证据，不能保证“最低风险”或免除平台自身责任。

| 候选 | 对本目标的适配 | 关键约束与判断 |
| --- | --- | --- |
| 平台收付通＋二级商户 | 官方说明支持二级商户收款、平台佣金与账期管理 | **首选核验并作为接入设计参考**：[产品介绍](https://pay.wechatpay.cn/doc/v3/partner/4012086891) 已有目标能力；行业与公司准入通过后沿用官方方案，当前不代表已获准开通 |
| 服务方商户收款＋普通服务商分账 | 将公司分成绑定原交易，避免依赖服务方事后主动转账 | 平台收付通不适用时再评估。[接入准备](https://pay.wechatpay.cn/doc/v3/partner/4012072589) 要求商户授权和分账权限；普通服务商不是直接收款商户。不能将其账期与收付通混用 |
| 公司收取全款，再分给个人服务方 | 技术上需核验公司作为收款方、服务方作为接收方的产品关系 | 不作为默认低风险方案。[普通商户分账](https://pay.wechatpay.cn/doc/v3/merchant/4012067962) 当前描述默认最高分账比例为 30%，不能直接假设能把大部分款项分给服务方；还需重新评估公司在真实交易中的责任 |
| 服务方收款后再自行向平台转佣金 | 没有将平台服务费结算绑定原交易 | 不满足稳定逐单分成的目标，不作为首版结算机制 |

**“稳定分成”的验收含义**：每笔订单确认分成规则快照；支付时建立正确商户及分账关系；验收后依据同一订单提交幂等分账；平台必须查到分成成功和账单，受理成功或页面数字不能代表到账。失败需可查询、重试与告警；普通订单不向用户开放跳过平台分成直接完结的业务入口。支付机构强制退款、风控或法定处理仍依其真实结果对账，不承诺任何交易均不可逆获利。

**退款和长履约检查**：全额退款、部分退款、已分账退款分别确定平台分成是否回退、由谁承担费用；每笔订单可退金额、平台分成与服务方实结金额必须核对一致。微信 [服务商分账常见问题](https://pay.wechatpay.cn/doc/v3/partner/4014547107) 说明分账受商户授权比例、结算和回退额度等约束。须核对最长可控账期与订单实际预约／履约长度，避免在验收前因产品期限到达而自动释放资金。

支付宝候选同时要满足“微信宿主可用入口”与“上述逐单分成、退款及结算”两组条件；仅能付款、仅有支付宝小程序支付或单独提供分账接口，都不能完成本目标。继续保留待证，未选定通道或服务商。

### 2.2 直接采用微信官方规则的实施基线

用户进一步要求直接参考微信成熟方案。本项目以平台收付通为首选适配路径，沿官方产品实施收款、分账、退款与对账；无需让用户重新设计这些技术规则。平台准入审核通过是正式接入前提，业务抽佣率与服务验收标准仍由公司确定。

| 官方已明确事项 | 对本项目的落实 |
| --- | --- |
| 服务方以二级商户身份收款，下单标记需分账；平台可发起分账及解冻 | 每笔合作关联真实服务方商户，验收后提交公司服务费分账，再完成剩余资金解冻；公司服务费到账与服务方银行卡到账分别核验 |
| 默认最长冻结 180 天，超期剩余资金自动解冻；默认分账上限 30% | 180 天不是本产品的验收等待期，30% 不是已决定的佣金率。按实际获批配置控制付款到结算时长，设置到期前处理和分账失败告警，不能无限等待验收 |
| 平台型电商合单支持 1—50 个二级商户；普通支付定位单商户独立小店 | 本项目为共享平台小程序，优先核对小程序合单接口；首版一笔合作仅含一个二级商户子单，不因此新增跨服务方购物车。以上依据 [产品介绍](https://pay.wechatpay.cn/doc/v3/partner/4012086891) |
| 公司先入驻普通服务商，再申请平台收付通并绑定 AppID；开通前不能已有普通模式子商户 | 按官方顺序办理，不先随意进件服务方。小微与个人卖家有不同定义，逐人选择真实主体类型并完成审核、签约及必要账户验证。依据 [接入准备](https://pay.wechatpay.cn/doc/v3/partner/4012086921) |
| 退款请求受理不代表退款成功；失败重试沿用原退款单号；退款期限为支付成功后 365 天 | 服务端保存独立退款事实，通知／查单确认结果；按累计金额限制退款。平台垫付退款属于另需申请的能力，首版不默认代服务方垫资。依据 [申请退款](https://pay.wechatpay.cn/doc/v3/partner/4012476892) |
| 已分账退款涉及回退；商户接收方需符合回退条件；微信交易类小程序还可能约束可结算时点 | 公司作为佣金接收商户核对回退授权，先核实回退与退款结果。服务验收必须衔接适用的微信订单管理规则，不能仅以自有“完成”状态强行分账。依据 [官方常见问题](https://pay.wechatpay.cn/doc/v3/partner/4012525463) |

**准入差距已缩小为具体检查**：官方 [能力页](https://pay.wechatpay.cn/static/partner_ability/business_payment.shtml) 列明主要面向实物撮合，并要求相应平台资质（ICP／EDI 等）和交易管理能力。摄影、后期、妆造、假发服务属于本项目实际场景，仍需匹配获准行业及公司实际资质；不能为了套用接口伪报经营类目，也不能把“资金在微信”表述为公司不承担平台责任。

开发顺序据此调整：先整理真实类目与平台资质差距；按上述确定规则编制入驻、单子单付款、验收分账、退款对账的接口与数据契约；具备商户权限后实接并做真机资金往返。公开规则已确定的部分不再作为开放问题逐项询问用户。支付宝保持独立可行性依赖，不反向阻塞微信确定部分。

## 3. 主流程与各方动作

以下为按已确认付款方式推导的实施方案。状态名称表达业务事实，不要求重命名已有订单阶段或新增平行系统。

| 环节 | 需求方 | 服务方 | 服务端放行条件与记录 |
| --- | --- | --- | --- |
| 协商与报价 | 提交需求、核对分项价格和时间 | 查看授权信息、确认服务条件及报价 | 复用现有预约；保留报价与服务快照，单项 ±15% 规则不变 |
| 缔约 | 阅读并确认本次合作条款，按需签署 NDA | 确认同版本条款，按需签署 NDA | 主体、服务、时间、金额、交付／验收、取消退款规则形成版本快照；双方确认可追溯 |
| 待付款 | 查看全额应付、选择已获准且可用的支付方式 | 查看待付款，不将其视为已成交收入 | 检查双方确认、必要 NDA、订单有效性和档期；按服务端金额建支付单 |
| 支付处理中 | 可返回查看结果，结果未知时可重新查询 | 查看待核验结果 | 以支付机构通知／查单核验商户、订单、金额和币种；客户端不能提交“我已支付”推进业务 |
| 已付款、可执行 | 查看付款凭证与合作进度 | 按约开始执行 | 足额付款核验通过，合同版本与占用有效；实际付款成功但占用冲突的异常须单独处理，不能丢弃付款事实 |
| 履约与交付 | 查看进度、接收交付，按约提出修改 | 更新进度、交付、修改后再提交 | 复用现有执行／修改／待验收阶段及文件事实；不同职业完成凭证按约定判定 |
| 验收通过 | 确认服务或交付符合约定 | 查看验收时间与待结算金额 | 记录验收事实，形成结算任务；验收和钱款到账分别保存 |
| 结算处理中 | 查看订单资金状态 | 查看结算受益账户、金额和处理状态 | 检查足额付款、验收、退款／争议及收款资格；幂等提交所选产品的结算指令 |
| 已结算 | 查看结算记录并评价 | 查看实际结算结果，可回复评价 | 依据支付机构结果记录；如仅到账支付账户，不能显示为已到账银行卡 |
| 售后 | 申请退款或争议处理，查看进度 | 提供处理意见和凭证 | 关联原订单与付款流水；退款、结算调整、处理责任和结果均可追溯 |

**评价建议**：继续沿用有效完成订单可评价，支付机构结算延迟不应抹去已完成履约事实；退款后统计是否保留、撤销或标记须单独确定，不自动修改历史评价。

**档期建议**：支付发起前先可靠占用，付款核验后转正式占用；未付超时要先确认支付关闭再释放。占用时长、职业容量和支付成功后的冲突处理方案仍待收口；本轮不设默认分钟数。

## 4. 取消、退款和争议的处理方案

以下提出必要分支与保护规则，不擅自设定违约金、退款比例或自动判责。

| 触发场景 | 处理方案 | 尚需决定 |
| --- | --- | --- |
| 未付款时退出收银台 | 保留待付事实，允许查询或在订单有效时重试；退出收银台不等于取消合作 | 支付截止时间、是否允许主动撤回 |
| 未付款订单取消或超时 | 查明支付状态，关闭仍可付的支付单；关闭确认后取消并释放占用 | 超时多久、通知对象与方式 |
| 取消与支付成功同时发生 | 保存真实收款；不将已收款写成未付款；根据订单有效性转履约或进入退款处理 | 自动退款可适用的明确场景 |
| 已付款、未开始执行 | 允许提出取消／改期申请并保存双方意见；退款审批和支付机构退款分开 | 取消责任、退款额度、是否允许改期及重签 |
| 已部分履约 | 保留进度、已交付内容及双方证据；按确认的处理结果形成退款或继续履约方案 | 部分履约计价、举证、谁有权裁决 |
| 待验收存在异议 | 修改、协商或申请介入；建议处理中暂停新的结算提交 | 修改次数、验收时限、运营处理时限与默认完成规则 |
| 退款批准 | 使用原支付关联的退款单提交；成功、处理中、失败分别展示；总退款不得超过可退实付 | 支付机构支持的退款窗口、手续费处理 |
| 已结算后发生退款 | 先核验分账回退／资金来源等通道能力，再执行退款并同步账单调整 | 退款资金责任与余额不足处理；不假设一定可追回已提现款 |

结算和退款并发须有互斥判定及可恢复记录：已经发出的指令应先查明结果，不能仅靠本地“暂停结算”标签撤回渠道侧资金操作。技术调用失败允许查询和重试，不自动改为退款拒绝或售后结案。

## 6. 必须通过的验收场景

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 任一方未确认、协议版本过时或必要 NDA 未完成 | 服务端拒绝建支付单和执行；页面指出缺失条件 |
| A02 | 客户端篡改金额或用别人的订单付款 | 不改变服务端应付金额、不产生越权流水；角色切换不能绕过 |
| A03 | 全额支付正常返回 | 同一订单仅认领一笔足额成功付款，双方刷新后事实一致 |
| A04 | 通知延迟／重复、客户端退出或弱网 | 查单恢复真实结果，重复通知不重复履约或记账 |
| A05 | 旧支付单未关闭就更换渠道 | 不产生并行可支付的有效订单；意外重复收款单独识别并按确定规则处理 |
| A06 | 付款成功恰逢取消、超时或档期冲突 | 收款事实保留；不会让冲突订单同时执行或无记录吞款 |
| A07 | 同一服务方跨日预约与同时抢档 | 全部实际占用时段被约束，只有符合容量规则的订单可成交 |
| A08 | 双方重复点击验收、结算回调重复或失败 | 验收记录不重复，结算只提交一次有效指令，失败可查询恢复 |
| A09 | 退款和结算同时申请 | 可退、可结金额由同一订单资金事实约束，无超退、超结 |
| A10 | 已结算售后、部分退款及退款失败 | 退款责任与资金来源明确，通道结果和两边账单一致，失败不显示退款完成 |
| A11 | 未安装支付宝、切换应用、支付后重进微信 | 候选路径在 iOS／Android 有真实结果与可理解的返回；未通过则支付宝仍未交付 |
| A12 | 两角色全流程及视觉验收 | 两位真实参与者从检索到售后；完整页、深层页面、空错态及窄屏保持清晰和品牌一致 |

### 8.3 服务端与页面的职责

1. 付款准备：可信身份确定需求方；服务端核验双方确认、必要 NDA、协议／报价版本、档期占用、商户资格与已配置的收费规则。任一不满足即返回可处理原因，不调用微信下单。
2. 下单成功：支付单先持久化；服务端取得并签名 prepay_id 后，仅向该付款人的专用响应返回短期支付参数，不将参数混入双方可读订单详情。
3. 结果同步：对已验签解密的通知／查单响应核对 AppID、平台／二级商户、合单／子单号、付款人、应付金额和币种，检查子单成功。付款事实与允许的履约推进在同一原子操作完成；非成功旧通知不能覆盖成功。
4. 异常支付：已收到足额付款但档期或订单失效时保存收款事实与异常原因，交既定退款／协调路径；不吞款、不直接强行进入执行。重复付款单独识别，不能变成第二份收入。
5. 验收结算：现有 COMPLETED 继续表示履约完成；分账、解冻、银行卡到账各有独立事实。旧 BUYER_ACCEPTS_AND_SETTLES 事件名不能证明结算已执行。
6. 回调入口：独立 HTTP 接收与 APIv3 验签／解密，不复用依赖微信调用上下文的普通 order-api。只有核验且可靠保存后才应答成功；重复通知幂等处理，内部错误不对外回显证件、密钥、完整签名或支付报文。
