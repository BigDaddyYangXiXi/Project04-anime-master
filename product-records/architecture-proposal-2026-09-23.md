# 万匠屋小程序架构改造方案｜待审阅

## 1. 目标与范围

在现有微信原生小程序、CloudBase 云函数、MySQL 和云存储基础上，完成以下改造：

1. 图片访问成本随实际浏览量增长，避免列表下载原图和无效预加载。
2. 列表和详情查询成本不再随全站作品、历史订单数量直接增长。
3. 订单、档期、支付和保密资料继续保持严格的身份与一致性约束。
4. 建立可观测、可限流、可降级的费用保护机制。
5. 通过真实设备和压力测试确定容量，不预先承诺支持多少在线用户。

本次不调整已批准的视觉设计、角色定义、交易阶段、金额规则和 NDA 规则。必要的加载、分页、错误及重试状态沿用现有组件。

不在首期引入独立服务器、Redis、搜索集群或额外 CDN。新增付费资源必须有现有能力不足的实测依据。

## 2. 目标架构

| 层级 | 职责 | 改造方向 |
|---|---|---|
| 小程序 | 展示、交互、按需加载 | 分页、图片规格选择、请求去重、返回状态恢复 |
| 公开目录接口 | 提供作品和服务方摘要 | 数据库筛选分页、按 ID 查询、短时缓存 |
| 交易接口 | 账号、订单、档期、支付 | 保留鉴权、幂等、事务；限制连接与请求并发 |
| 媒体处理 | 校验、审核、生成展示图片 | 固定规格、异步处理、失败重试 |
| 云存储与 CDN | 保存文件、分发图片 | 公开展示图与私有材料隔离、稳定版本地址 |
| 运维保障 | 监控、预算、恢复 | 用量告警、限流降级、备份与恢复演练 |

图片文件不通过普通业务云函数逐张转发。业务接口返回元信息和访问地址，图片由存储/CDN 分发。

## 3. 图片系统改造

### 3.1 区分媒体类别

| 类别 | 访问规则 | 展示方式 |
|---|---|---|
| 公开作品、头像、公开须知 | 审核和发布通过后可公开访问 | 稳定版本地址、共享 CDN 缓存 |
| 草稿及待审核图片 | 所有人及必要的后台处理可访问 | 私有访问，不进入公开路径 |
| 项目参考图、保密资料 | 按身份、项目及 NDA 状态授权 | 授权后访问 |
| 订单交付附件 | 按订单参与者和阶段授权 | 私有下载，记录必要的访问事件 |

不能仅依靠前端隐藏图片或使用难猜的文件名保护私有内容。

公开展示副本应由可信服务端写入，客户端不能覆盖已审核的公开文件。原始上传路径与公开发布路径分离。

### 3.2 建立固定图片规格

首期只生成必要版本：

| 版本 | 初始目标 | 使用位置 |
|---|---|---|
| 头像 | 128～256 像素，约 10～30 KB | 用户与服务方头像 |
| 列表封面 | 480～640 像素宽，约 40～100 KB | 发现、搜索、收藏、作品列表 |
| 详情图 | 1080～1600 像素宽，约 150～400 KB | 作品正文与图集 |
| 原图 | 保留原始质量 | 明确查看原图及必要交付 |

这些是性能目标，不是强制画质阈值。摄影、插画、透明图和长图使用实际样本验收；保留宽高比，不自动裁掉作品内容。

公开衍生图片移除不必要的定位等元数据。原始交付文件保持业务所需内容。

### 3.3 上传与处理流程

上传准备 → 私有直传 → 服务端验证 → 内容审核与图片处理 → 满足条件后发布。

实现要求：

- 复用现有媒体资产 ID、上传接口和审核状态，不重建一套媒体系统。
- 增加衍生文件、宽高、字节数、处理版本和处理状态记录。
- 审核通过与图片处理成功分别记录；公开发布需要两者都满足。
- 处理任务按“资产 ID＋处理版本”幂等执行，限制重试次数和并发。
- 处理失败保留草稿并允许重试，不默认把大原图当列表封面。
- 衍生图与原文件共同纳入引用检查、删除和孤儿文件清理。
- 修复媒体校验中写死旧环境 ID 的问题。

优先比较现有平台图片处理能力与一个专用处理函数的成本和限制，只选择一种实现。首期采用上传后一次生成，避免每次浏览重复处理。

### 3.4 缓存与撤回

公开文件使用包含版本的路径，内容变化生成新地址。列表、详情和原图分别引用对应版本。

下架或审核撤销时，停止目录输出，并删除或封禁公开副本、清理 CDN 缓存。缓存和已下载文件不能保证瞬间全部收回，保密材料因此始终保留在私有链路。

## 4. 目录与数据库改造

### 4.1 从全量读取改为定向查询

现有目录接口保留，逐步替换内部实现：

- 发现与搜索：数据库完成城市、职业、状态等筛选与分页。
- 服务方详情：只查询该服务方，作品和评价分别分页。
- 作品详情：只查询该作品及必要的服务方、服务摘要。
- 列表：只返回展示字段、封面和必要统计，不返回完整作品图集。
- 前端实际接续分页游标，处理无更多、加载失败及筛选变化。

作品模式按作品分页，服务方模式按服务方分页，避免“分页服务方后展开全部作品”造成页面大小不可控。

### 4.2 保留发布快照，增加必要的查询字段

保留现有发布快照和版本规则。先检查已有作品、标签、服务和地域表能否复用，仅补足查询必需的字段与索引。

若快照中的字段无法高效筛选，再增加最小的公开目录查询表，包含：

- 作品与服务方 ID；
- 发布版本、状态、职业与地域信息；
- 查询所需的价格、标签；
- 封面资产、排序字段。

查询表只用于查找和展示，不能成为订单价格、资格或档期的最终依据。

发布时同步更新快照及查询数据；若需要异步更新，必须有可靠待办记录、幂等处理及定期核对机制，避免发布成功却永远搜不到。

### 4.3 统计与档期

评分、评价数、完成单量不再在每次浏览时扫描历史订单。保存必要的汇总结果，并提供重算核对方式。

档期按服务方和日期范围读取，避免扫描该服务方全部历史订单。最终确认合作仍通过事务复核，不因展示缓存而放宽占档规则。

### 4.4 缓存

首期使用有限容量、短有效期的公开目录缓存和客户端状态复用，不新增独立缓存服务。

缓存键必须包含影响结果的筛选条件、分页和版本。账户切换时清理用户相关缓存，私有数据不进入共享目录缓存。

缓存失效或函数冷启动时，直接数据库查询也必须能够承受目标流量，不能把缓存命中作为唯一保障。

## 5. 前端流畅度改造

影响范围包括发现、搜索、服务方详情、作品详情、收藏、个人作品、橱窗编辑及涉及媒体的订单页面。

复用共享卡片、图集和媒体服务，避免逐页新增不同规则。

具体改造：

- 首屏优先加载，只预取邻近内容。
- 列表使用封面版本，详情按需加载详情图。
- 返回列表保留滚动位置和已有内容。
- 相同请求合并，快速切换筛选时忽略过期响应。
- 重试有次数与间隔限制；写操作重试保持原幂等键。
- 长列表控制节点数量和数据更新范围。
- 给图片预留正确宽高比例，减少加载后跳动。
- 图片错误只影响对应图片，不让整页无法使用。

实施前运行模块影响面检查，覆盖所有登记消费者。完成后更新清单并执行设计检查；不借性能改造扩大视觉调整范围。

## 6. 生产安全与稳定性

### 6.1 新环境接入

先验证当前套餐的 VPC 权益、TLS 证书与主机名、数据库应用账号及连接能力，不预设必须升级。

数据库使用最小权限账号；订单事务保持证书与主机名校验，不为接通而关闭验证。

公网支付或微信接口与数据库内网访问是否需要拆分，在官方调用通路、费用和失败恢复明确后决定；不先购买 NAT。

### 6.2 数据与交易

保留现有可信身份、角色校验、版本控制、幂等及事务占档。

补充验证：

- 重复点击、请求超时后重试，不产生重复订单或重复入账。
- 同一档期并发争抢，只允许符合规则的操作成功。
- 支付回调重复、乱序、延迟时结果仍正确。
- 用户不能通过猜测资产 ID、文件地址或订单 ID 越权读取。

函数扩容上限、连接池大小和数据库连接额度统一设计，避免函数扩容压垮数据库。

### 6.3 可恢复性

建立数据库和媒体的备份策略，并完成一次真实恢复演练。备份频率、保留期和恢复时间依据业务容忍度确定，不仅验证“已开启备份”。

日志不保存密钥、完整签名下载地址或保密正文；规定保留期，避免日志本身成为持续增长的费用。

## 7. 费用控制

费用模型统一为：

月成本＝基础套餐＋超额分发流量＋存储＋图片处理＋函数和数据库＋日志备份＋必要网络服务。

分项核对套餐抵扣和独立计费，避免重复计算。持续记录：

- 每千次列表浏览的图片流量；
- 每千次目录请求的数据库和函数消耗；
- 每千张上传图片的处理及存储成本；
- 每笔订单的业务请求成本。

保护措施：

| 层级 | 控制 |
|---|---|
| 单用户 | 上传次数、总容量、原图访问和高成本接口频率 |
| 单接口 | 页大小、参数范围、请求频率、最大在途请求 |
| 图片分发 | 防盗刷、访问阈值、源站绕过防护 |
| 全局 | 累计用量、短时突增、预计月费用告警 |

限流需要覆盖多实例，不能只靠单个函数进程中的计数。优先利用平台现有能力，并验证适用于当前调用方式。

预算达到预警线时先减少预加载和原图服务，优先保护已有订单、付款核对和必要交付。费用控制可能延迟生效，需要预留缓冲；不能承诺绝对零超支。

具体月预算暂记为 B，方案阶段不虚构用户可接受的金额。

## 8. 分阶段实施与回退

| 阶段 | 主要工作 | 完成条件 |
|---|---|---|
| 0：建立基线 | 核验云配置、权限、套餐、现有耗时与流量；确定测试数据规模 | 有可复测的基线和风险清单 |
| 1：接入与安全底座 | 环境校验、TLS、应用账号、媒体权限、基本限流与监控 | 双账号隔离及关键事务验证通过 |
| 2：图片链路 | 固定规格、处理流程、公开私有隔离、统一图片访问 | 真实样本画质合格，流量目标达成 |
| 3：查询与分页 | 定向查询、查询字段与索引、统计汇总、前端分页 | 不再按全站数据读取，结果完整正确 |
| 4：容量与费用保护 | 压测、弱网、预算降级、备份恢复 | 得到实测容量、费用范围和可执行运行手册 |
| 5：小范围上线 | 配套部署、受控用户验证、观察指标 | 满足上线门槛后逐步扩大访问 |

迁移采用增量方式：

- 新字段和新接口响应先兼容旧客户端。
- 有数据的库先核对并备份，再迁移，不根据历史“空库”记录直接操作。
- 新查询与旧查询先在测试环境比对结果。
- 通过少量明确的发布开关切换读取路径，不建立复杂配置系统。
- 图片和数据库新结构稳定前不急于删除旧结构。
- 回退不得把私有内容改为公开，也不得撤销已完成的支付或订单事实。

老接口若在回退时存在容量风险，回退必须同时限流，不能直接恢复无限制的全量读取。

## 9. 验收标准

以下为第一轮建议目标，阶段 0 固定测试设备、网络、数据量及测量口径后执行：

| 指标 | 初始目标 |
|---|---|
| 列表图片 | 相同样本和清晰度要求下，下载字节比原图方案下降至少 80% |
| 首屏 | 指定中端真机及约定网络下，95% 的测试在 2.5 秒内看到首批内容 |
| 目录接口 | 目标压力下，95% 请求在 800 毫秒内完成 |
| 非预期错误 | 持续压力测试中低于 0.5%；限流拒绝单独统计 |
| 数据正确性 | 分页完整；常规翻页无重复；筛选语义与现有契约一致 |
| 安全 | 跨账号读取、未经审核公开、直接覆盖公开文件等测试均被拒绝 |
| 交易 | 并发确认、重复请求及重复支付通知不破坏业务一致性 |
| 费用保护 | 模拟异常访问，证明限流、告警及降级实际生效 |
| 恢复 | 实际恢复成功，并记录恢复时间与数据恢复点 |

压测分别覆盖目录读取、图片分发和订单写入，不把三者混为一个“并发人数”。同时测试冷缓存、热门内容集中访问和大量不同图片访问。

测试使用独立数据并设置费用和停止条件。最终容量取满足正确性、延迟及错误率要求的持续承载能力，并预留余量，不以瞬时峰值作为上线承诺。

## 10. 决策建议

建议批准的技术路线是：

**保留现有架构，先完成接入安全、图片分级和数据库定向查询，再以实测结果确定套餐与扩容。**

上线规模尚未确定时，先按分档压力测试设计，不提前购买“大并发套餐”。增加独立缓存、专用搜索或常驻服务，必须同时满足：

1. 已证明现有优化后仍有明确瓶颈；
2. 已算清新增固定费用和运维成本；
3. 有可验证的收益与回退办法。
