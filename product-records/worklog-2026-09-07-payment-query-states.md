# P06b 第二步：未支付与已关闭查询状态 — 2026-09-07

内部 payment-api 升至 `0.4.0`，客户端仍为 `0.7.0-native.11`，18 个数据库迁移不变。沿用此前原始响应验签与商户绑定规则，本批增加 NOTPAY、PAYERROR、CLOSED 的可信处理。内部方法改名为 `queryPayment` 和 `acceptPaymentQuery`，删除旧的仅成功方法名并更新调用方，没有保留无用兼容层。

## 官方依据与取舍

[平台收付通合单查询订单](https://pay.wechatpay.cn/doc/v3/partner/4012761049) 的查询响应允许缺少付款人及交易类型。9 月 7 日直接读取超时，通过同一官方页面搜索索引核对字段；只对未支付／关闭结果接受这些字段缺省，绝不以数据库里的 OpenID 补造渠道返回值。字段存在时仍须有效，付款人须与原付款人匹配；合单、子单、AppID、平台及二级商户仍全部核对。

该页面正文提及 USERPAYING 查询场景，但交易状态枚举未列出 USERPAYING；本项目也未开放付款码支付。因此暂时保持不支持，不混用“指定身份合单支付”或普通支付的枚举来宣称已支持。REFUND 不等于退款完成，仍交由后续退款记录与对账流程处理；未知状态保持失败，不能当作未付款。

## 状态与页面对应

| 渠道结果 | 数据库与服务规则 | 页面结果 |
| --- | --- | --- |
| NOTPAY／PAYERROR | 在订单锁内核对当前支付记录，只读返回渠道观察和当前存储状态；不将支付单标为 CLOSED，不降级已到账状态 | 保持现有订单事实；不会把已经确认付款的页面退回付款按钮，也不会产生资金记录 |
| CLOSED，当前支付单为 CREATED | 原支付单改为 CLOSED。仅当合作仍待需求方最终确认、订单处于 VERIFYING、且无其他未关闭支付单时，同事务恢复 UNPAID 并记录关闭事件和新版本 | 需求方退出“等待支付结果确认”，复用现有继续付款按钮；服务方仍在等待需求方确认／付款，不进入执行 |
| 重复 CLOSED／旧支付单 CLOSED | 不再次改订单、不重复事件；已关闭旧单不能清除新支付单的核验状态 | 新支付流程和页面状态保持原状 |
| 已付款后收到 NOTPAY、PAYERROR 或 CLOSED | 以数据库已有到账事实为准，不删除交易号、不撤销付款 | 需求方与服务方仍显示付款已确认；资金记录保持 |
| CLOSED 后迟到 SUCCESS | 沿用到账事实保留与 PAYMENT_REVIEW；其他关闭操作不能清除待核对状态 | 双方显示付款待核对并阻止重复付款；不直接执行或结算 |
| 关闭记录或订单恢复写入失败 | 整个事务回滚，支付单和订单一致保留原状态 | 不把仍在核验中的订单误呈现为可再次付款 |

关闭一笔支付尝试不是取消双方合作。确认信息、服务条件、业务阶段均保留，下一笔付款仍必须通过服务端原有协议、商户、费率、版本及唯一活动付款检查。未支付查询是瞬时观察，不额外创建“到账”或“收入”记录。

## 验证与限制

- 通用回归 **181／181**；真实 MySQL 集成 **22／22**，全部 18 个迁移通过。
- 新增缺省付款人、不允许放宽成功通知、待支付观察不降级到账、重复关闭、旧关闭遇到新付款、关闭恢复整体回滚等测试。
- 已验证模拟微信签名 CLOSED 响应 → 实际查询方法 → 真实数据库 → 订单权限读取 → 客户端映射 → 需求方与服务方页面方法。需求方恢复 UNPAID 与继续付款提示，服务方保持等待状态；没有新增重复画面。
- 完整测试输出位于 `wechat-miniprogram/.artifacts/payment-query-states/`。隔离 MySQL 已关闭，未调用真实微信接口，未部署或上传体验版。

本批是内部查询恢复，客户端付款后刷新尚未接入渠道查询。完整页、真机、生产网络及公开查询权限入口仍未验收，不能称为支付能力可用。SUCCESS 仍要求完整付款人及成功事实；缺失付款人的成功款项如何以可审计方式进入待核对、原始公网回调适配、实际关单请求和恢复任务是下一步。商户、费率、生产事务连接及 F07 规则前置继续保留。
