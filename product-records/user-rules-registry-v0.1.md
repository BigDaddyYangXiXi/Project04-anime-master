# 《动漫高手》用户规范台账 v0.1

> 文档性质：项目记录文档，不是跨项目纲领文件。  
> 用途：持续记录需求方规范、服务方规范和全局性规范，并把每条规范映射为可实现、可测试的产品表达。  
> 状态口径：`已确认`＝用户已经明确；`已确认原则／待细化`＝方向明确但参数或边界未定；`原型验证规则`＝已进入当前原型、尚待业务确认；`建议草案`＝产品建议，不代表已经决定；`待定`＝仅登记问题。

## 1. 台账字段

| 字段 | 说明 |
|---|---|
| 规范编号 | `D` 需求方、`S` 服务方、`G` 全局规则 |
| 触发条件 | 哪个行为或状态触发规则 |
| 规则内容 | 可被产品和运营共同理解的原子规则 |
| 产品功能表达 | 页面、控件、校验、提示、状态或后台动作 |
| 数据与审计 | 为判定、申诉和复盘必须留下的数据 |
| 状态 | 已确认程度，不把建议写成正式规则 |

## 5. 待确认问题

1. “协商中”从需求方发送邀请开始，还是从服务方接受沟通开始计数？
2. 服务方婉拒、任一方撤回、超时未响应分别何时释放协商名额？
3. 同一需求方对同一服务者重复发起，按一条会话还是多条预约计数？
4. 企业会员的 50 条额度属于企业主体共享，还是每位获授权员工各有 50 条？
5. 违规积分是需求方、服务方分别计分，还是同一账户共享一个全局分？
6. 处罚阈值、申诉期间是否暂停处罚、积分恢复周期如何定义？

## 6. 产品实现约束

- 所有硬限制必须由服务端判定，前端只负责提示和引导。
- 每次规则判定保存规则版本，避免规则调整后无法解释历史结果。
- 达到额度时必须告诉用户：当前用量、额度上限、释放额度的方法；只有商业额度不足才展示升级入口。
- 任何限制展示都要有可访问的规则说明；涉及处罚时必须提供证据摘要与申诉入口。
- 新增规范时先进入本台账，再进入 PRD、状态机和原型，避免页面规则与文档脱节。
