# 首发需求对账与验收范围

日期：2026-09-05。代码基线：`26f22e6`／`0.7.0-native.7`。本轮只改项目记录；不修改业务代码、不调用生产业务接口、不恢复支付开发或第二账号 QA。

## 1. 对账结论和状态口径

已对照原 PRD 的 FR-01—FR-10、用户台账 23 条规则及会员权限草案。功能页齐全不代表业务规则已落实；已有 132 项测试通过记录不覆盖本轮新识别的所有缺口，也不替代真机或双账号验收。

- **实现待验**：找到代码路径及相关历史测试，尚缺当前版本真实操作证据。
- **部分实现**：存在明确未实现的子要求或规则不一致，不能仅补截图关闭。
- **未见实现**：在当前一方客户端、云函数及 17 个迁移中未发现对应业务路径；不等于断言其他外部系统绝不存在。
- **规则待决**：历史仍为草案／待定，或新旧表述需确定边界；不擅自变成开发要求。
- **被新规则替代**：保留原要求与替代依据，不重新实现旧流程。

当前首发里程碑仍待用户选择。下文非支付体验范围为建议，不是已经批准的删减；支付与第二账号 QA 暂停状态继续有效。

## 2. 首发范围选项

| 里程碑 | 要验证的结果 | 不能据此宣称完成 | 依赖 |
| --- | --- | --- | --- |
| A：非支付封闭体验（建议） | 真实账号资料、供给编辑发布、城市发现、作品、档期、收藏、项目及预约沟通的可用性；付款处有明确不可用反馈 | 支付后执行、交付、验收和评价的真实全链路；正式交易上线 | 平台配置、隐私／字段披露、准入边界和本轮缺口处理；完整预约正向验收仍需另行恢复双账号测试 |
| B：完整交易上线版缺口梳理 | 将付款、退款、资金对账、履约、运营和必要资格全部纳入发布门槛 | 仅选择 B 不等于恢复支付开发、接受资金方案或放开第二账号测试 | 业务规则与平台资格先明确，随后另行恢复实施和测试 |

两个选项都不能把所有用户默认具备接单资格、未保护的敏感需求或错误档期直接当作可上线状态。选择 A 也不自动允许线下转账绕过现有支付门禁；封闭体验不等于正式市场开放。

## 7. 历史规则的替代与待决边界

1. **项目槽位**：旧 FR-06 的预设职业槽位／缺人提示被后续 D-006 与 UI 标准 10.3 的执行订单连续列表替代；不重建旧槽位。项目只管理，不推进订单。
2. **沟通方式和执行入口**：旧 PRD 的沟通方式待定、纯确认后执行，已由 UI 标准 9.6／支付规则收敛为站外联系、四项确认、必要 NDA、买方确认及服务端核验付款。支付门禁继续有效。
3. **Brief**：当前 D-007 是从历史预约整理草稿；它只证明该流程被确认，不足以认定原智能抽取能力整体取消。AI 提取是否进入首发仍待决定。
4. **毛娘履约**：旧 PRD 标记待定，当前代码和 9 月 3 日交付日志按现场类处理；尚未找到足以替代业务确认的明确决策，本轮不把实现当确认。
5. **普通平均分与综合评分**：普通平均分实现为完成单有效评价平均、保留一位小数；它不证明综合评分窗口／权重和热门标签算法已获批准。
6. **作品码唯一性**：服务端短哈希稳定生成不等于严格唯一性约束；删除后的历史引用规则原本待定，仍保留待决。
