# 动漫高手

## 项目状态

- 当前阶段：原生小程序与真实后端集成，非支付体验验收与发布收口（2026-09-05）
- 产品形态：微信小程序；本地目标版本 `0.7.0-native.7`
- 需求状态：主业务已实现；首发范围、交易及运营要求仍需逐项对账，不能据页面完成认定可正式上线

## 当前目标

先建立可信工程基线，再冻结首发范围、完成微信能力整改和当前版本真实数据往返验收。支付开发和第二账号 QA 沿用暂停状态，恢复后再完成真实交易闭环。当前状态与任务验收统一见 [工程基线与任务台账](product-records/development-baseline.md)，续接进度见 [当前检查点](current-task-checkpoint.md)。

`prototype/` 保留独立 Git 历史；根目录仓库管理项目文档、设计资料与 `wechat-miniprogram/`，不重复纳入原型仓库。本地版本基线不等于云端部署或公众平台上传确认。

## 项目纲领与执行约束

### 1. 产品形态与规范边界

- 《动漫高手》是基于微信生态开发的**微信小程序**，不是通用 H5、独立 App 或仅用于展示的网页。
- 信息架构、页面尺寸、导航与返回、固定底栏、滚动容器、触控区域、安全区、授权、隐私、支付及平台审核等设计与实现，必须受微信小程序官方开发要求约束。
- 当需求或批注与微信小程序规范冲突时，执行者必须在修改前指出冲突、说明影响，并给出符合规范的等价方案；不得默默照做，也不得以“低保真”为由忽略平台约束。
- Figma 中为验证流程建立的地域、日期时间、高级筛选等预设组件仅用于交互测试，不是生产实现。打包微信小程序前必须替换为微信原生 `picker`、`picker-view`、`checkbox-group`、`button` 或符合小程序规范的 WXML/WXSS 自定义组件，并重新验证安全区、层级、返回、表单状态与真机行为。

### 2. 历史意见继承

- 新版本必须继承此前已确认且未被明确推翻的修改意见。低保真线框只降低视觉细节，不得擅自删除既有功能、页面结构或交互逻辑。
- 修改前至少读取：`current-task-checkpoint.md`、原型 `CHANGELOG.md`、相关版本设计契约、历次批注处理记录、进度记录及当前源代码；涉及线上批注时还必须读取完整 `/api/comments` 数据。
- 决策优先级为：用户当前明确指令 → 最新已确认批注或设计契约 → 历史批注闭环与开发日志 → 当前发布基线。发现冲突时必须显式记录，不能自行选择后覆盖历史。

### 3. 双分支开发

- 在线 `Prototype` 与互动 `Wireframe` 独立迭代、独立记录版本。线框修改不得直接覆盖在线原型，在线原型继续供同事批注。
- 合并前必须建立清单，明确源 Prototype 版本、源 Wireframe 版本、目标 Prototype 版本，以及纳入、排除和冲突处理项。
- 在只完成局部页面时必须如实标明范围，不得将“单页修正”描述成“已完整还原全部 0.7”。

### 4. 记录与验收

- 所有 UI、Figma、原型和小程序修复，在修改前与验收前都必须读取 `prototype/docs/UI-QUALITY-STANDARD.md`。它是尺寸、间距、组件连续性、状态矩阵和验收证据的唯一公共规范入口。
- 每轮工作日志记录：输入依据、修改范围、关键决定、版本变化、验证结果和未完成项。
- 错误记录必须包含：现象、原因、影响、修复和预防措施；工具失败后先检查是否产生半成品，再决定是否重试。
- 交付前应按改动风险验证页面尺寸、关键交互、跳转目标、返回关系、固定导航、滚动与触控区域，并保持文档状态与实际 Figma／代码一致。
